CONTEXTO
--------
Este documento recoge los hallazgos técnicos obtenidos durante el diseño,
implementación y ejecución real del proyecto de automatización API para
Demoblaze, usando Karate DSL 1.5.2 con JUnit 5 y Maven sobre Java 17.

Resultados finales verificados:
  mvn test               → 10/10 escenarios PASSED | BUILD SUCCESS
  mvn test -Dtest=SmokeTest  → 2/2 escenarios PASSED  | BUILD SUCCESS

================================================================================
1. COMPORTAMIENTO REAL DE LA API (verificado en ejecución)
================================================================================

1.1  HTTP 200 en todos los casos — ausencia de semántica REST
-------------------------------------------------------------
La API retorna código 200 tanto en operaciones exitosas como en errores
funcionales. Esto viola el estándar HTTP/REST donde corresponderían:
  - 201 Created      → creación exitosa de usuario
  - 409 Conflict     → intento de registrar usuario duplicado
  - 401 Unauthorized → credenciales inválidas

IMPACTO EN QA: No es posible distinguir éxito de error por el status code.
Las validaciones deben inspecionar el body de la respuesta.

DECISIÓN: Se valida `status 200` como indicador de disponibilidad del servicio,
y se agrega validación semántica del body en cada escenario.

1.2  Signup exitoso retorna string JSON vacío
---------------------------------------------
Al registrar un usuario nuevo, la API retorna:

  HTTP 200
  Content-Type: application/json
  Body: ""

El body es un string JSON con valor vacío — no un objeto, no null, no ausente.

IMPACTO EN KARATE: El uso de `match response == ""` falla porque Karate
deserializa `""` como string vacío `''` y la comparación literal no coincide
con el schema leído desde archivo. La solución correcta es usar el marcador
semántico de Karate `"#string"` en el schema externo.

LECCIÓN: Para respuestas primitivas en Karate, siempre usar marcadores
`#string`, `#number`, `#boolean` en lugar de valores literales.

1.3  Login exitoso retorna string plano (no JSON)
-------------------------------------------------
La autenticación exitosa retorna un string con Content-Type: application/json:

  "Auth_token: dGVzdF9leGlzdGluZ191c3IxNzgxNjYy"

El valor es el username codificado en Base64 seguido de un timestamp.
No es un JWT estándar (no tiene header.payload.signature). La implementación
es básica y no provee expiración ni claims verificables sin decodificación.

VALIDACIONES APLICADAS:
  1. match response == schema  → tipo string
  2. match response contains 'Auth_token:'  → formato correcto del prefijo

1.4  Login distingue dos tipos de error con mensajes diferentes
---------------------------------------------------------------
La API diferencia con precisión entre dos escenarios negativos de login:

  Usuario no existe:  {"errorMessage": "User does not exist."}
  Password incorrecto: {"errorMessage": "Wrong password."}

Esta distinción permite diseñar dos escenarios negativos independientes
y validar con exactitud el mensaje esperado en cada caso.

RIESGO DE SEGURIDAD (hallazgo): Este comportamiento permite a un atacante
determinar si un usuario existe en el sistema mediante enumeración de usuarios
(username enumeration attack). Una API con buenas prácticas de seguridad
retornaría el mismo mensaje genérico en ambos casos.

1.5  Persistencia de datos entre ejecuciones
--------------------------------------------
La API pública Demoblaze no provee mecanismo de teardown (DELETE de usuarios).
Los usuarios creados en pruebas persisten indefinidamente en el servidor.

DECISIÓN para TC-001: Username generado con timestamp (user_1718046523421)
garantiza unicidad en cada ejecución sin necesidad de limpieza previa.
Esto hace el escenario idempotente y seguro para ejecuciones múltiples.

DECISIÓN para TC-002 (caso obligatorio - usuario duplicado):
Este escenario es completamente autónomo. NO depende de ningún usuario
preexistente en el servidor compartido de Demoblaze. El flujo es:
  Paso 1: Registrar un usuario nuevo dinámico (dup_<timestamp>) → ""
  Paso 2: Intentar registrar el mismo usuario nuevamente → errorMessage

================================================================================
2. DECISIONES DE DISEÑO
================================================================================

2.1  Centralización de credenciales en karate-config.js
-------------------------------------------------------
Las variables testUser y testPassword se definen UNA VEZ en karate-config.js
y se consumen por referencia (#(testUser)) en todos los payloads JSON.

BENEFICIOS:
  - Un solo punto de cambio si el usuario de prueba cambia.
  - Permite sobreescribir desde línea de comandos:
      mvn test -DtestUser=otro_usuario -DtestPassword=otra_clave
  - Lee la propiedad primero de System.properties (Maven) y usa el valor
    por defecto si no se provee. Patrón:
      karate.properties['testUser'] || 'test_existing_usr'

2.2  Payloads con expresiones Karate (#(variable))
---------------------------------------------------
Los payloads JSON externos usan expresiones de interpolación de Karate:
  {"username": "#(testUser)", "password": "#(testPassword)"}

Karate resuelve estas expresiones en tiempo de ejecución usando las variables
del contexto actual (inicializadas por karate-config.js).

2.3  Schemas semánticos con marcadores Karate
--------------------------------------------
Los schemas usan marcadores en lugar de valores literales:
  "#string"              → cualquier string (incluyendo vacío)
  {"errorMessage":"#string"} → objeto con campo errorMessage de tipo string

Esto garantiza que los schemas validan ESTRUCTURA y TIPO, no valores concretos.
Los valores concretos se validan en pasos adicionales:
  match response.errorMessage == 'This user already exist.'

2.4  Scenario Outline para cobertura ampliada
--------------------------------------------
Ambas features usan Scenario Outline con Examples para demostrar cobertura
múltiple sin duplicación de código Gherkin.

El Outline de login incluye flag `useConfigPass` para resolver si el password
viene del karate-config.js (testPassword) o del valor literal de la tabla.
Esto es necesario porque las celdas de la tabla Examples no pueden contener
expresiones Karate (#(variable)).

2.5  Diseño autónomo de TC-002 (caso obligatorio de duplicado)
--------------------------------------------------------------
El caso "intentar registrar usuario existente" fue diseñado para NO depender
de ningún dato preexistente en el servidor. El escenario ejecuta dos llamadas:
  1. POST /signup con usuario dinámico dup_<timestamp> → espera ""
  2. POST /signup con el MISMO usuario → espera {errorMessage:...}

Esto elimina el riesgo de fallo por datos fuera de control del proyecto
(usuario que no existe, fue eliminado, o tiene otro password).

Como consecuencia, el payload `signup-existing.json` fue eliminado porque
quedó sin uso: TC-002 construye su propio payload dinámicamente.

2.6  Caso TC-007: Login con usuario inexistente (caso adicional de valor)
------------------------------------------------------------------------
Se agregó TC-007 como escenario independiente (no solo en Outline) para
distinguir explícitamente entre "Wrong password." y "User does not exist.".
Este caso cubre una ruta de error diferente y valida el mensaje exacto.

La inclusión es justificada: los 4 casos obligatorios del reto están cubiertos
(TC-001, TC-002, TC-005, TC-006) y TC-007 agrega cobertura real sin repetir
alcance.

2.7  Jerarquía de tags para segmentación de ejecución
-----------------------------------------------------
  @smoke @critical  → Escenarios imprescindibles (TC-001, TC-005)
  @regression       → Escenarios de regresión completa
  @negative         → Flujos de error esperados
  @positive         → Flujos felices
  @signup / @login  → Segmentación por endpoint
  @outline          → Escenarios con tabla de datos

Esto permite filtrar por cualquier combinación:
  mvn test -Dkarate.options="--tags @negative"
  mvn test -Dkarate.options="--tags @signup"
  mvn test -Dtest=SmokeTest   ← ejecuta solo @smoke

================================================================================
3. LIMITACIONES ENCONTRADAS
================================================================================

3.1  No hay teardown de datos de prueba
Los usuarios creados en TC-001 y TC-003 (outline) no se eliminan al finalizar
las pruebas. La API no provee endpoint DELETE para usuarios. Con el tiempo,
se acumulan usuarios de prueba en el servidor compartido de Demoblaze.

3.2  API pública sin aislamiento de ambiente
Demoblaze es una API pública compartida. Otro equipo o automatización podría
afectar los datos de prueba (ej: eliminar o modificar test_existing_usr).
En un proyecto real se recomendaría un ambiente propio o datos de prueba
controlados por el equipo.

3.3  Token no es JWT estándar
El token retornado por /login no puede validarse como JWT. No tiene claims
(sub, exp, iat). Esto limita las validaciones posibles sobre el token al
simple prefijo "Auth_token:" y tipo string.

3.4  Sin validación de campos vacíos o nulos en signup
La API Demoblaze no maneja correctamente ciertos casos extremos como username
vacío o nulo. Durante las pruebas exploratorias se observó que la API puede
no retornar un error claro para entradas inválidas. Se decidió no incluir
estos casos en el alcance del reto para no generar falsos positivos.

4. MEJORAS FUTURAS
================================================================================

1. Implementar un Background pre-condición para crear el usuario de prueba
   al inicio del feature de login, garantizando independencia total de datos
   preexistentes. Esto haría el proyecto 100% autónomo.

2. Agregar validación del token decodificando el Base64:
     def decoded = karate.fromBase64(token)
   Y verificar que contiene el username esperado.

3. Agregar un escenario E2E: signup de nuevo usuario → login inmediato
   con las mismas credenciales. Justificado como flujo de usuario completo.

4. Implementar paralelismo controlado con `Karate.run(...).parallel(N)` para
   reducir el tiempo de ejecución de la suite de regresión.

5. Configurar CI/CD (sin GitHub Actions) con ejecución automática y publicación
   del reporte HTML como artefacto del pipeline.

================================================================================
5. VALORACIÓN DE KARATE DSL
================================================================================

FORTALEZAS:
  ✓ Sintaxis Gherkin legible — los escenarios son documentación viva
  ✓ Zero boilerplate para HTTP — no requiere clases Java adicionales
  ✓ Reporte HTML integrado — disponible sin plugins adicionales
  ✓ Marcadores semánticos (#string, #null, #array) — validación expresiva
  ✓ karate.call() — reutilización de lógica entre features (patrón helper)
  ✓ Interpolación en payloads (#(variable)) — datos desacoplados del código
  ✓ karate.properties — sobreescribir config desde Maven sin tocar código

DEBILIDADES:
  ✗ Expresiones dentro de Examples tables — no se pueden usar variables Karate
    directamente en celdas; requiere flags auxiliares (useConfigPass)
  ✗ Debugging — menos intuitivo que Java puro; errores de JS en if() inline
  ✗ IDE support — IntelliSense limitado en archivos .feature

================================================================================
6. CONCLUSIÓN GENERAL
================================================================================

La solución desarrollada cumple satisfactoriamente los requisitos planteados en
el reto técnico, automatizando los procesos de registro y autenticación de
usuarios mediante Karate DSL, JUnit 5 y Maven.

Además de los cuatro escenarios solicitados originalmente, se incorporaron
casos adicionales orientados a ampliar la cobertura funcional, validar rutas
alternativas y demostrar el uso de funcionalidades avanzadas del framework,
como Scenario Outline, reutilización de componentes y validación mediante
schemas externos.
Durante la implementación se aplicaron buenas prácticas de automatización:

• Separación de datos de prueba, payloads y schemas.
• Configuración centralizada mediante karate-config.js.
• Uso de datos dinámicos para evitar dependencias externas.
• Validaciones basadas en el comportamiento real de la API.
• Generación automática de reportes para facilitar el análisis de resultados.

Uno de los hallazgos más relevantes fue identificar que la API utiliza el
código HTTP 200 tanto para respuestas exitosas como para errores funcionales.
Por esta razón, las validaciones fueron diseñadas considerando el contenido
del body de la respuesta y no únicamente el código de estado HTTP.

Asimismo, se identificaron oportunidades de mejora relacionadas con la gestión
de errores, el manejo de tokens de autenticación y la independencia de los
datos de prueba, aspectos que fueron documentados como recomendaciones futuras.

En conclusión, este ejercicio permitió demostrar competencias en:

• Automatización de APIs REST.
• Diseño y ejecución de casos de prueba.
• Análisis de comportamiento de servicios.
• Validación de respuestas y contratos.
• Documentación técnica de hallazgos.
• Uso de Karate DSL para pruebas automatizadas.


El resultado final es una solución funcional, mantenible y fácilmente
ejecutable, alineada con los objetivos del reto técnico y con prácticas
comúnmente utilizadas en proyectos de aseguramiento de calidad de software.
